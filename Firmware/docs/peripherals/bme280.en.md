# BME280 sensor (temperature / pressure / humidity) — I2C

## Overview

The Bosch BME280 (temperature / pressure / humidity, chip id `0x60`) is owned by
the **RISC-V MCU** running RT-Thread. It shares **I²C0** with the ICM-42670-P and
is exposed to Linux through the MCU's **`SensorService`** on the rpmsg channel
**`rpmsg-sensor`**, endpoint **`0x4006`**. The BME280 answers at address
**`0x76`**.

Linux has no active kernel binding for the chip on-device (the bus is disabled);
it opens the rpmsg endpoint and reads compensated values from userspace via the
**`sensor_test`** client (`src/sensor-client/`). The MCU-side driver does the
I²C transfers (`HAL_I2C` polling) and the Bosch compensation math.

## Driving it from Linux

`sensor_test` opens the `rpmsg-sensor` endpoint and issues one SensorService
command per invocation. The underlying protocol opcodes are `PING`, `WHOAMI`,
`BME280_READ` and `IMU_READ`; the client subcommands map onto them:

| Subcommand | Purpose |
|------------|---------|
| `ping` | Verify the SensorService responds (id `SENS`) |
| `whoami bme` | Read the BME280 chip id (expect `0x60`) |
| `bme` | Read compensated temperature, pressure and humidity |
| `all` | `bme` + `imu` in one call |
| `help` | Usage |

**Example invocations:**

```bash
sensor_test ping           # SensorService alive?
sensor_test whoami bme     # -> 0x60
sensor_test bme            # -> temperature / pressure / humidity
```

## Hardware reference (physical device)

Wiring of the BME280 on the board, independent of who drives it. For the full
pin-ownership map (which subsystem claims each GPIO) see
[`../architecture/peripheral-ownership.md`](../architecture/peripheral-ownership.md).

| BME280 pin | I2C signal | RV1106 GPIO | Mux |
|------------|------------|-------------|-----|
| SCK / SCL  | i2c0_scl   | GPIO1_A3    | i2c0 m0 (func 2) |
| SDI / SDA  | i2c0_sda   | GPIO1_A4    | i2c0 m0 (func 2) |
| SDO        | address    | GND → `0x76` · VDDIO → `0x77` | — |
| CSB        | selects I2C | tie to VDDIO | — |

Bus: **I2C0**, mux **m0**. Default address **0x76** (SDO to GND). The MCU owns
this bus and shares it with the ICM-42670-P at `0x68`.

## Legacy: Linux kernel driver (reference only)

> **This path does NOT bind on-device.** `&i2c0` is `status = "disabled"` in the
> DTS (ceded to the MCU — see the banner), so the mainline IIO driver never probes.
> It is retained as the wiring/register reference for the MCU driver and for
> readers who resurrect the Linux-driven path. The sysfs details below are for
> that case.

Historically the BME280 was driven by the **mainline IIO `bmp280` driver**
already present in the kernel tree (`drivers/iio/pressure/bmp280-*`). The same
driver covers BMP180/BMP280/BME280; it detects the BME280 by its `0x60` chip id
and exposes the extra humidity channel. **No custom driver or `.ko` is needed**:
it is built into the kernel (`CONFIG_BMP280=y`) and the device-tree node bound
automatically at boot.

### Kernel configuration

In `configs/kernel/rv1106_minimal_defconfig`:

```
CONFIG_I2C=y            # I2C subsystem (was missing: without it RK3X/CHARDEV get dropped)
CONFIG_I2C_RK3X=y       # Rockchip I2C controller
CONFIG_BMP280=y         # IIO driver (selects REGMAP, BMP280_I2C, REGMAP_I2C)
CONFIG_BMP280_I2C=y
```

`CONFIG_BMP280=y` pulls in `BMP280_I2C` and `REGMAP_I2C` via `select`, so the
I2C glue (`bmp280-i2c`) is built automatically.

### Device tree (`dts/rv1106-sdk-ipc.dtsi`)

> Historical Linux-bind node. In the current tree `&i2c0` is `status = "disabled"`
> (ceded to the MCU — see the banner above); the snippet below reflects the retained
> Linux-driver approach.

```dts
&i2c0 {
	status = "okay";
	pinctrl-names = "default";
	pinctrl-0 = <&i2c0m0_xfer>;   /* GPIO1_A3=SCL, GPIO1_A4=SDA */
	clock-frequency = <400000>;

	bme280: bme280@76 {
		compatible = "bosch,bme280";
		reg = <0x76>;
	};
};
```

`compatible = "bosch,bme280"` matches the driver's `of_match` table and pins the
BME280 chip id. The `i2c0m0_xfer` pin-group maps exactly to GPIO1_A3/A4.

### Testing via the Linux driver

The driver exposed the sensor as an IIO device in sysfs. After boot:

> **IIO device index.** The SoC SARADC is left **disabled** in this SDK
> (`&saradc { status = "disabled"; }`), so the BME280 is the only IIO device and
> sits at `iio:device0`. It is still safest to locate it by name in case another
> IIO peripheral is enabled later:
>
> ```sh
> # List every IIO device with its name
> for d in /sys/bus/iio/devices/iio:device*; do echo "$d -> $(cat $d/name)"; done
> # expected:  iio:device0 -> bme280
> ```

```sh
# Is the bus up and the chip at 0x76?
i2cdetect -y 0                 # should show 'UU' at 0x76 (claimed by the driver)

cat /sys/bus/iio/devices/iio:device0/name          # -> bme280

# Readings (IIO "raw" values):
cat /sys/bus/iio/devices/iio:device0/in_temp_input              # milli-°C (e.g. 23450 = 23.45 °C)
cat /sys/bus/iio/devices/iio:device0/in_pressure_input          # kPa
cat /sys/bus/iio/devices/iio:device0/in_humidityrelative_input  # milli-% RH
```

> Exact attribute names may vary by version; if you see `in_*_raw` + `in_*_scale`
> instead of `in_*_input`, the real value is `raw × scale`. List the directory
> with `ls /sys/bus/iio/devices/iio:device0/`.

If no `iio:device*` reports the name `bme280`, check `dmesg | grep -i bmp280` for
the probe and any bus/address errors.
