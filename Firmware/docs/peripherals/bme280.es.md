# Sensor BME280 (temperatura / presión / humedad) — I2C

## Descripción general

El BME280 de Bosch (temperatura / presión / humedad, chip-id `0x60`) lo posee el
**MCU RISC-V** corriendo RT-Thread. Comparte **I²C0** con el ICM-42670-P y se
expone a Linux a través del **`SensorService`** del MCU en el canal rpmsg
**`rpmsg-sensor`**, endpoint **`0x4006`**. El BME280 responde en la dirección
**`0x76`**.

Linux no tiene bind de kernel activo para el chip en placa (el bus está
deshabilitado); abre el endpoint rpmsg y lee valores compensados desde userspace
vía el cliente **`sensor_test`** (`src/sensor-client/`). El driver del lado MCU
hace las transferencias I²C (`HAL_I2C` por polling) y la matemática de
compensación de Bosch.

## Manejo desde Linux

`sensor_test` abre el endpoint `rpmsg-sensor` y emite un comando del
SensorService por invocación. Los opcodes del protocolo subyacente son `PING`,
`WHOAMI`, `BME280_READ` e `IMU_READ`; los subcomandos del cliente mapean a
ellos:

| Subcomando | Propósito |
|------------|-----------|
| `ping` | Verifica que el SensorService responde (id `SENS`) |
| `whoami bme` | Lee el chip-id del BME280 (se espera `0x60`) |
| `bme` | Lee temperatura, presión y humedad compensadas |
| `all` | `bme` + `imu` en una sola llamada |
| `help` | Ayuda |

**Ejemplos de invocación:**

```bash
sensor_test ping           # ¿SensorService vivo?
sensor_test whoami bme     # -> 0x60
sensor_test bme            # -> temperatura / presión / humedad
```

## Referencia de hardware (dispositivo físico)

Cableado del BME280 en la placa, independiente de quién lo maneje. Para el mapa
completo de propiedad de pines (qué subsistema reclama cada GPIO) ver
[`../architecture/peripheral-ownership.md`](../architecture/peripheral-ownership.md).

| Pin BME280 | Señal I2C | GPIO RV1106 | Mux |
|------------|-----------|-------------|-----|
| SCK / SCL  | i2c0_scl  | GPIO1_A3    | i2c0 m0 (func 2) |
| SDI / SDA  | i2c0_sda  | GPIO1_A4    | i2c0 m0 (func 2) |
| SDO        | dirección | GND → `0x76` · VDDIO → `0x77` | — |
| CSB        | selecciona I2C | atar a VDDIO | — |

Bus: **I2C0**, mux **m0**. Dirección por defecto **0x76** (SDO a GND). El MCU
posee este bus y lo comparte con el ICM-42670-P en `0x68`.

## Legado: driver de kernel Linux (solo referencia)

> **Esta ruta NO hace bind en placa.** `&i2c0` está `status = "disabled"` en el
> DTS (cedido al MCU — ver el banner), así que el driver IIO mainline nunca hace
> probe. Se conserva como referencia de cableado/registros para el driver del MCU
> y para quien resucite la ruta manejada por Linux. Los detalles sysfs de abajo
> son para ese caso.

Históricamente el BME280 se manejaba con el **driver IIO mainline `bmp280`** que
ya viene en el árbol del kernel (`drivers/iio/pressure/bmp280-*`). El mismo
driver soporta BMP180/BMP280/BME280; detecta el BME280 por su chip-id `0x60` y
expone el canal extra de humedad. **No hace falta un driver propio ni un `.ko`**:
se compila dentro del kernel (`CONFIG_BMP280=y`) y el nodo del device tree hacía
*bind* automáticamente al arrancar.

### Configuración del kernel

En `configs/kernel/rv1106_minimal_defconfig`:

```
CONFIG_I2C=y            # subsistema I2C (faltaba: sin él RK3X/CHARDEV se descartan)
CONFIG_I2C_RK3X=y       # controlador I2C de Rockchip
CONFIG_BMP280=y         # driver IIO (selecciona REGMAP, BMP280_I2C, REGMAP_I2C)
CONFIG_BMP280_I2C=y
```

`CONFIG_BMP280=y` arrastra por `select` a `BMP280_I2C` y `REGMAP_I2C`, así que
el glue I2C (`bmp280-i2c`) se construye solo.

### Device tree (`dts/rv1106-sdk-ipc.dtsi`)

> Nodo histórico de bind por Linux. En el árbol actual `&i2c0` está
> `status = "disabled"` (cedido al MCU — ver el banner de arriba); el snippet de
> abajo refleja el enfoque conservado del driver Linux.

```dts
&i2c0 {
	status = "okay";
	pinctrl-names = "default";
	pinctrl-0 = <&i2c0m0_xfer>;   /* GPIO1_A3=SCL, GPIO1_A4=SDA */
	clock-frequency = <400000>;

	bme280: bme280@76 {
		compatible = "bosch,bme280";
		reg = <0x76>;
	};
};
```

`compatible = "bosch,bme280"` coincide con la tabla `of_match` del driver y le
fija el chip-id BME280. El pin-group `i2c0m0_xfer` mapea exactamente a
GPIO1_A3/A4.

### Pruebas vía el driver Linux

El driver exponía el sensor como un dispositivo IIO en sysfs. Tras arrancar:

> **Índice del dispositivo IIO.** El SARADC del SoC se dejó **deshabilitado** en
> este SDK (`&saradc { status = "disabled"; }`), así que el BME280 es el único
> dispositivo IIO y queda en `iio:device0`. Aun así conviene localizarlo por
> nombre por si en el futuro se habilita otro periférico IIO:
>
> ```sh
> # Lista todos los dispositivos IIO con su nombre
> for d in /sys/bus/iio/devices/iio:device*; do echo "$d -> $(cat $d/name)"; done
> # esperado:  iio:device0 -> bme280
> ```

```sh
# ¿Aparece el bus y el chip en 0x76?
i2cdetect -y 0                 # debería marcar 'UU' en 0x76 (ocupado por el driver)

cat /sys/bus/iio/devices/iio:device0/name          # -> bme280

# Lecturas (valores "crudos" del IIO):
cat /sys/bus/iio/devices/iio:device0/in_temp_input              # mili-°C  (p.ej. 23450 = 23.45 °C)
cat /sys/bus/iio/devices/iio:device0/in_pressure_input          # kPa
cat /sys/bus/iio/devices/iio:device0/in_humidityrelative_input  # mili-% HR
```

> Los nombres exactos de los atributos pueden variar según la versión; si en vez
> de `in_*_input` ves `in_*_raw` + `in_*_scale`, el valor real es
> `raw × scale`. Lista el directorio con `ls /sys/bus/iio/devices/iio:device0/`.

Si no aparece ningún `iio:device*` con nombre `bme280`, revisa
`dmesg | grep -i bmp280` para ver el *probe* y posibles errores de bus/dirección.
