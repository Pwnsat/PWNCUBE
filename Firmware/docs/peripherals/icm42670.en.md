# ICM-42670-P — 6-axis IMU (accelerometer + gyroscope) — I2C

## Overview

The TDK InvenSense ICM-42670-P (6-axis IMU, `WHO_AM_I = 0x67`) is owned by the
**RISC-V MCU** running RT-Thread. It shares **I²C0** with the BME280 and is
exposed to Linux through the MCU's **`SensorService`** on the rpmsg channel
**`rpmsg-sensor`**, endpoint **`0x4006`**. The IMU answers at address **`0x68`**.

Linux has no active kernel binding for the chip on-device (the bus is disabled);
it opens the rpmsg endpoint and reads accel/gyro/temperature from userspace via
the **`sensor_test`** client (`src/sensor-client/`). The MCU-side driver does the
I²C transfers (`HAL_I2C` polling) using the register map ported from the retained
Linux driver.

> The mainline `inv_icm42600` driver only covers ICM-42600/42602/42605/42622 — a
> different family with a different register map — so the ICM-42670-P register
> access was implemented from scratch (see the legacy appendix).

## Driving it from Linux

`sensor_test` opens the `rpmsg-sensor` endpoint and issues one SensorService
command per invocation. The underlying protocol opcodes are `PING`, `WHOAMI`,
`BME280_READ` and `IMU_READ`; the client subcommands map onto them:

| Subcommand | Purpose |
|------------|---------|
| `ping` | Verify the SensorService responds (id `SENS`) |
| `whoami icm` | Read the IMU chip id (expect `0x67`) |
| `imu` | Read acceleration, angular rate and temperature |
| `all` | `bme` + `imu` in one call |
| `help` | Usage |

**Example invocations:**

```bash
sensor_test ping           # SensorService alive?
sensor_test whoami icm     # -> 0x67
sensor_test imu            # -> accel / gyro / temperature
```

## Hardware reference (physical device)

Wiring of the ICM-42670-P on the board, independent of who drives it. It shares
the **I2C0 bus** with the BME280. For the full pin-ownership map (which subsystem
claims each GPIO) see
[`../architecture/peripheral-ownership.md`](../architecture/peripheral-ownership.md).

| ICM-42670-P pin | Signal | RV1106 GPIO | Use |
|-----------------|--------|-------------|-----|
| AP_SCKL (13) | I2C SCL | GPIO1_A3 | i2c0 m0 (shared with BME280) |
| AP_SDI (14)  | I2C SDA | GPIO1_A4 | i2c0 m0 (shared with BME280) |
| AP_AD0 (1)   | address | GPIO0_A5 | **gpio-hog low → 0x68** |
| INT1 (4)     | data-ready IRQ | GPIO0_A1 | wired (unused) |
| INT2 (9)     | secondary IRQ | GPIO0_A0 | reserved |
| FSYNC (7)    | frame sync | GPIO0_A2 | reserved |

**I2C address: 0x68.** AP_AD0 is routed to a GPIO, held low so the address is
pinned deterministically. For 0x69, drive AP_AD0 high.

## Legacy: Linux kernel driver (reference only)

> **This driver does NOT bind on-device.** `&i2c0` is `status = "disabled"` in the
> DTS (ceded to the MCU — see the banner), so `icm42670.ko` never probes. It is
> retained as the register-map reference for the MCU driver and for readers who
> resurrect the Linux-driven path. The sysfs details below are for that case.

The ICM-42670-P **has no driver in kernel 5.10.160** (the mainline `inv_icm42600`
only covers ICM-42600/42602/42605/42622, a different family with a different
register map). This SDK therefore shipped a **dedicated IIO driver**
(`icm42670.ko`), packaged like the SX1262.

It is a minimal driver: soft reset, check `WHO_AM_I = 0x67`, power accel + gyro in
low-noise mode, and expose data over sysfs read on demand (no FIFO or
interrupt-driven buffer — read with `cat`, like the BME280).

### Driver (`src/icm42670-kmod/icm42670.c`)

- I2C + regmap. IIO channels: `accel_{x,y,z}`, `anglvel_{x,y,z}`, `temp`.
- Default config: max full scale (±16 g, ±2000 dps) at 100 Hz.
- Scales exposed via `in_*_scale` (raw value × scale → SI units).

Built by the **`icm42670`** package (`PKG_ENABLE_icm42670=y`), installs
`/lib/modules/5.10.160/icm42670.ko`, loaded by `rcS` at boot.

### Device tree (`dts/rv1106-sdk-ipc.dtsi`)

> Historical Linux-bind node. In the current tree `&i2c0` is `status = "disabled"`
> (ceded to the MCU — see the banner above); the snippet below reflects the
> retained Linux-driver approach.

```dts
&i2c0 {
	icm42670: icm42670@68 {
		compatible = "invensense,icm42670p";
		reg = <0x68>;
		pinctrl-names = "default";
		pinctrl-0 = <&icm42670_pins>;
		interrupt-parent = <&gpio0>;
		interrupts = <RK_PA1 IRQ_TYPE_LEVEL_HIGH>;  /* INT1 */
	};
};

&gpio0 {
	icm42670_ad0_hog: icm42670-ad0-hog {
		gpio-hog;
		gpios = <RK_PA5 GPIO_ACTIVE_HIGH>;  /* AP_AD0 */
		output-low;                          /* -> 0x68 */
	};
};
```

### Testing via the Linux driver

```sh
# chip at 0x68?
i2cdetect -y 0                 # 'UU' at 0x68 (claimed by the driver)

# Locate the IIO device by name (index may vary):
for d in /sys/bus/iio/devices/iio:device*; do echo "$d -> $(cat $d/name)"; done
# find the one named 'icm42670'

D=/sys/bus/iio/devices/iio:deviceN     # N = the icm42670 one
cat $D/in_accel_x_raw $D/in_accel_y_raw $D/in_accel_z_raw   # raw (× in_accel_scale = m/s^2)
cat $D/in_anglvel_x_raw $D/in_anglvel_y_raw $D/in_anglvel_z_raw  # × in_anglvel_scale = rad/s
cat $D/in_temp_raw     # (raw + in_temp_offset) × in_temp_scale = milli-degC
cat $D/in_accel_scale $D/in_anglvel_scale
```

At rest, `accel_z` should read ~1 g (≈ 8192 raw at ±16 g) and the gyro ~0. If it
does not appear, check `dmesg | grep -i icm42670` (it prints the `WHO_AM_I` value
when it does not match 0x67).

### Legacy notes

- MVP without FIFO/IRQ: one-shot sysfs reads. INT1/INT2/FSYNC are wired for adding
  an interrupt-driven buffer later.
- The temperature formula (`raw/128 + 25 °C`) is approximate; the focus is
  accel/gyro.
