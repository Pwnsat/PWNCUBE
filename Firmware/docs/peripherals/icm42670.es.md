# ICM-42670-P — IMU de 6 ejes (acelerómetro + giroscopio) — I2C

## Descripción general

El ICM-42670-P de TDK InvenSense (IMU de 6 ejes, `WHO_AM_I = 0x67`) lo posee el
**MCU RISC-V** corriendo RT-Thread. Comparte **I²C0** con el BME280 y se expone a
Linux a través del **`SensorService`** del MCU en el canal rpmsg
**`rpmsg-sensor`**, endpoint **`0x4006`**. La IMU responde en la dirección
**`0x68`**.

Linux no tiene bind de kernel activo para el chip en placa (el bus está
deshabilitado); abre el endpoint rpmsg y lee accel/giro/temperatura desde
userspace vía el cliente **`sensor_test`** (`src/sensor-client/`). El driver del
lado MCU hace las transferencias I²C (`HAL_I2C` por polling) usando el mapa de
registros portado del driver Linux conservado.

> El driver mainline `inv_icm42600` solo cubre ICM-42600/42602/42605/42622 —otra
> familia con mapa de registros distinto— así que el acceso a registros del
> ICM-42670-P se implementó desde cero (ver el apéndice de legado).

## Manejo desde Linux

`sensor_test` abre el endpoint `rpmsg-sensor` y emite un comando del
SensorService por invocación. Los opcodes del protocolo subyacente son `PING`,
`WHOAMI`, `BME280_READ` e `IMU_READ`; los subcomandos del cliente mapean a ellos:

| Subcomando | Propósito |
|------------|-----------|
| `ping` | Verifica que el SensorService responde (id `SENS`) |
| `whoami icm` | Lee el chip-id de la IMU (se espera `0x67`) |
| `imu` | Lee aceleración, velocidad angular y temperatura |
| `all` | `bme` + `imu` en una sola llamada |
| `help` | Ayuda |

**Ejemplos de invocación:**

```bash
sensor_test ping           # ¿SensorService vivo?
sensor_test whoami icm     # -> 0x67
sensor_test imu            # -> accel / giro / temperatura
```

## Referencia de hardware (dispositivo físico)

Cableado del ICM-42670-P en la placa, independiente de quién lo maneje. Comparte
el **bus I2C0** con el BME280. Para el mapa completo de propiedad de pines (qué
subsistema reclama cada GPIO) ver
[`../architecture/peripheral-ownership.md`](../architecture/peripheral-ownership.md).

| Pin ICM-42670-P | Señal | GPIO RV1106 | Uso |
|-----------------|-------|-------------|-----|
| AP_SCKL (13) | I2C SCL | GPIO1_A3 | i2c0 m0 (compartido con BME280) |
| AP_SDI (14)  | I2C SDA | GPIO1_A4 | i2c0 m0 (compartido con BME280) |
| AP_AD0 (1)   | dirección | GPIO0_A5 | **gpio-hog a low → 0x68** |
| INT1 (4)     | data-ready IRQ | GPIO0_A1 | cableado (sin usar) |
| INT2 (9)     | IRQ secundaria | GPIO0_A0 | reservado |
| FSYNC (7)    | frame sync | GPIO0_A2 | reservado |

**Dirección I2C: 0x68.** AP_AD0 va a un GPIO, mantenido a nivel bajo para fijar
la dirección de forma determinista. Para usar 0x69, lleva AP_AD0 a alto.

## Legado: driver de kernel Linux (solo referencia)

> **Este driver NO hace bind en placa.** `&i2c0` está `status = "disabled"` en el
> DTS (cedido al MCU — ver el banner), así que `icm42670.ko` nunca hace probe. Se
> conserva como referencia del mapa de registros para el driver del MCU y para
> quien resucite la ruta manejada por Linux. Los detalles sysfs de abajo son para
> ese caso.

El ICM-42670-P **no tiene driver en el kernel 5.10.160** (el `inv_icm42600` de
mainline solo cubre ICM-42600/42602/42605/42622, que son de otra familia con mapa
de registros distinto). Por eso este SDK traía un **driver IIO propio**
(`icm42670.ko`), empaquetado como el SX1262.

Es un driver mínimo: hace reset, verifica `WHO_AM_I = 0x67`, enciende
acelerómetro y giroscopio en *low-noise*, y expone los datos por sysfs leídos
bajo demanda (sin FIFO ni buffer por interrupción — se lee con `cat`, igual que
el BME280).

### Driver (`src/icm42670-kmod/icm42670.c`)

- I2C + regmap. Canales IIO: `accel_{x,y,z}`, `anglvel_{x,y,z}`, `temp`.
- Config por defecto: fondo de escala máximo (±16 g, ±2000 dps) a 100 Hz.
- Escalas expuestas vía `in_*_scale` (valores crudos × escala → unidades SI).

Empaquetado por el paquete **`icm42670`** (`PKG_ENABLE_icm42670=y`), instala
`/lib/modules/5.10.160/icm42670.ko`, cargado por `rcS` al arrancar.

### Device tree (`dts/rv1106-sdk-ipc.dtsi`)

> Nodo histórico de bind por Linux. En el árbol actual `&i2c0` está
> `status = "disabled"` (cedido al MCU — ver el banner de arriba); el snippet de
> abajo refleja el enfoque conservado del driver Linux.

```dts
&i2c0 {
	icm42670: icm42670@68 {
		compatible = "invensense,icm42670p";
		reg = <0x68>;
		pinctrl-names = "default";
		pinctrl-0 = <&icm42670_pins>;
		interrupt-parent = <&gpio0>;
		interrupts = <RK_PA1 IRQ_TYPE_LEVEL_HIGH>;  /* INT1 */
	};
};

&gpio0 {
	icm42670_ad0_hog: icm42670-ad0-hog {
		gpio-hog;
		gpios = <RK_PA5 GPIO_ACTIVE_HIGH>;  /* AP_AD0 */
		output-low;                          /* -> 0x68 */
	};
};
```

### Pruebas vía el driver Linux

```sh
# ¿chip en 0x68?
i2cdetect -y 0                 # 'UU' en 0x68 (tomado por el driver)

# Localiza el dispositivo IIO por nombre (el índice puede variar):
for d in /sys/bus/iio/devices/iio:device*; do echo "$d -> $(cat $d/name)"; done
# busca el que diga 'icm42670'

D=/sys/bus/iio/devices/iio:deviceN     # N = el del icm42670
cat $D/in_accel_x_raw $D/in_accel_y_raw $D/in_accel_z_raw   # crudos (× in_accel_scale = m/s^2)
cat $D/in_anglvel_x_raw $D/in_anglvel_y_raw $D/in_anglvel_z_raw  # × in_anglvel_scale = rad/s
cat $D/in_temp_raw     # (raw + in_temp_offset) × in_temp_scale = mili-°C
cat $D/in_accel_scale $D/in_anglvel_scale
```

En reposo, `accel_z` debería marcar ~1 g (≈ 8192 crudo a ±16 g) y los giros
~0. Si no aparece, revisa `dmesg | grep -i icm42670` (imprime el `WHO_AM_I` si
no coincide con 0x67).

### Notas de legado

- MVP sin FIFO/IRQ: lectura puntual por sysfs. INT1/INT2/FSYNC quedan cableados
  para añadir buffer por interrupción más adelante.
- La fórmula de temperatura (`raw/128 + 25 °C`) es aproximada; el foco son
  accel/giro.
